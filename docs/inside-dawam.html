Chapter 1

What this thing actually is

A planner whose clock is the sun, that works with the network unplugged, and that only recently learned to have an account.

Dawam has an unusual shape for a modern app, and every unusual thing about it follows from one decision: the device is the source of truth.

part 1

One React app

Built by into plain static files. There is no server rendering anything — the whole app is downloaded once and then runs entirely in the browser.

the source of truth

localStorage

Your planner is a handful of keys in the browser's own storage: planner:settings, planner:pool, one key per week, one per day of points. Clear site data and the planner is gone — which is why export exists.

part 3

A service worker

Precaches the entire app and its fonts, so Dawam opens with the plane in flight mode. This is what makes it a rather than a website.

part 4, optional

An account, if you want one

Sign in with Google and the whole planner becomes one document per account in Postgres. It is a background reconciliation, not a dependency — turn it off and nothing about the app changes.

The sentence that explains the whole design

Dawam is local-first. Not “offline-capable” — local-first, which is a stronger claim: the local copy is authoritative and the network is an optimisation. That one decision explains why storage is wrapped in a fake-async API, why sync is a merge rather than a fetch, why conflicts must resolve without a server arbitrating, and why a rendering never waits for a request.

The trade is honest: no spinner ever blocks you from ticking something off, and in exchange you own the backup problem, and two devices editing the same week on the same day can lose one edit. Chapter 6 is exactly how much that costs and why it was accepted.

Check yourself: the API is down for a day. What stops working?

Chapter 3

The sun as a clock

Dawam's day is not divided into hours. It is divided into six blocks whose boundaries move with the sun, computed on the device from first principles.

Most planners would fetch prayer times from an API. Dawam computes them, which means the app works with no network, in any city, on any date — and it means there is real astronomy in your codebase.

With the sun's position known, each prayer becomes “the moment the sun is at a given angle below the horizon”, and the whole table falls out of one helper.

Why this matters beyond Dawam

This is a worked example of a pattern worth recognising: a problem that looks like it needs a server (“where do I get prayer times?”) is actually a closed-form calculation someone published decades ago. Before adding a network dependency, it is always worth asking whether the answer is computable. Every dependency you avoid is a failure mode you never have to handle.

Chapter 4

Now: one thing at a time

The Now view shows a single task. Everything interesting about it is in what it refuses to do.

A list of twenty things is a list you avoid. Dawam's Now view surfaces exactly one item; checking it reveals the next. That is a product decision, but it creates an engineering obligation, and the comment above the code states it in capital letters.

The rule

The Now queue must mirror the Plan page exactly. If Now surfaces tasks in a different order than Plan lists them, the app appears to be making decisions you did not ask for — and the user loses the ability to predict what comes next, which is the whole benefit of one-at-a-time. That is why line 1244 sorts by the same three keys the Plan page uses, in the same order.

Note the second thing that comment settles: the queue starts at the beginning of the day, not at the current block. Filtering to “only the current prayer period” would be the obvious implementation and it silently abandons anything you did not finish this morning. The queue is the whole day; the block only colours the screen.

The sky, and why the interface changes colour

The background is not decoration. It is interpolated continuously between ten reference points across the day, using exactly the technique a dynamic wallpaper uses — so the app looks like the time it is, and glancing at it tells you roughly where in the day you are before you read anything.

Check yourself: what would happen to a task you left unfinished in the Fajr block if nowList filtered to the current block?
Chapter 5

Storage, and a ledger that cannot lie

Forty-three lines of storage, ninety lines of accounting, and two ideas worth stealing for every project you build after this one.

Start with storage. It is localStorage, which is synchronous — but every function here returns a promise anyway.

Now the points ledger, which is the most professionally-designed file in the repo for its size. Two ideas carry it, and both are worth learning by name.

Two ideas worth stealing

Derive, do not store. There is no balance field anywhere; the balance is the sum of the ledger, computed every time. A stored balance can drift out of agreement with its history — and once it has, you cannot tell which one is wrong. A derived one cannot.

Idempotency keys. Every entry carries a ref naming its source. Awarding a ref that already exists is dropped. That is the same mechanism a payment processor uses to make sure a retried charge does not bill twice, and it is why ticking, unticking and re-ticking a task cannot mint points.

Check yourself: you tick a task, untick it, and tick it again. How many points are you paid, and what does the ledger look like afterwards?
Chapter 6

Sync, and the bug that shaped it

Two devices, no coordination, no change log, no vector clocks — and a merge function that is provably safe to run in either direction.

This is the hardest chapter and the most valuable. Read the file's own header comment first, because it names the bug the whole design is built around.

The document, and why it merges per key

Dawam already stores its planner as independent localStorage keys — settings, the pool, one per week. Those keys are the records, so merging per key gives you conflict resolution for free.

The two properties that matter

Symmetric: merge(a,b) and merge(b,a) hold the same content. Idempotent: merging twice changes nothing. Together those mean the server can merge blindly — it does not need to know who edited what or in which order, and a request that arrives twice is harmless. Almost all of the complexity people associate with sync is the price of not having these two properties.

The deterministic serialiser, and the loop it killed

Now the part that reads like a war story, because it is one. Asking “has this document changed?” with JSON.stringify compares key order — and key order is an artefact of how an object happened to be built. The server built the merged document one way, migrate() rebuilt it another, and an unchanged document therefore compared unequal on every single round trip.

The result: push, adopt, see a difference, push again — forever, a few seconds apart, while the user is trying to type.

Law

Never compare two objects for equality with JSON.stringify. It is the most common version of this bug in the whole industry and it is invisible in testing, because in a test both objects are usually built by the same code path. If you need structural equality, sort the keys — which is exactly what stable() does, in nine lines.

Chapter 7

The two optional halves: notifications and AI

One only exists inside the Android shell; the other only exists if you supply a key. Both are written so their absence changes nothing.

Dawam ships as a PWA and as an Android app built with . Native notifications only make sense in the second one, so every export in notify.js is a no-op on the web.

Android trap worth remembering

Android freezes a notification channel's importance when the channel is first created and ignores every later change. So correcting importance means publishing a new channel id — hence rhythm-reminders-v2. A device that already made v1 would otherwise keep the wrong behaviour forever, short of reinstalling. Versioned channel ids are the standard workaround and almost nobody discovers them before shipping the bug.

The AI transport, and the switch that was removed

The brain-dump sorter, the planning assistant and task sizing all share one transport: Gemini primary, Groq as an automatic fallback. The interesting decision is negative — there is deliberately no provider switch.

An earlier version had one, and it was a trap: a key for one provider entered while the toggle pointed at the other made every AI feature die with a 401 and nothing to say why. One primary, one backup, zero configuration to get wrong.

The second decision is subtler and worth internalising. The fallback fires only on outage-type failures — unreachable, rate-limited, 5xx — and never on configuration errors. A bad key fails loudly instead of being papered over by a silent second provider, because a silent fallback turns a five-minute fix into a mystery.

Check yourself: Gemini returns 401 because the key was pasted with a trailing space. Should Dawam fall back to Groq?
Chapter 8

181 tests, and the 2,241-line file

Look at what is tested and what is not. The pattern is not an accident, and it is the single most transferable idea in this tour.

That last row is the lesson. Every rule that would be expensive to get wrong has been pulled out of the UI into a file that takes values in and returns values out — and those files are where all 181 tests live. What remains in App.jsx is assembly: state, handlers, JSX. Assembly is reviewable by eye and cheap to change; rules are not.

So the honest answer to “should App.jsx be split up?” is: splitting it would make it tidier and would not make it safer, because the dangerous parts already left. If you ever do split it, split it along the same line — by extracting more rules, not by moving more markup.

Chapter 9

Change it yourself

Four exercises, in order of difficulty. Each one uses a different layer of what you have just read.

  1. Change a constant. CAIRO in core.jsx holds the latitude, longitude and the Fajr/Isha angles. Point it at another city and watch every block boundary in the app move. Then read tests/core.test.js and see which tests you just broke — and whether they should have been.
  2. Add a block hint. Each entry in BLOCKS carries hint and hintAr. Change one and note that the Arabic ships beside the English in the same object, rather than in a separate translation file — a deliberate choice for a two-language app of this size.
  3. Add a points rule. Pay for completing a whole block, not just a task. New ref shape (block:<id>:<iso>), an award call, and a test in points.test.js proving it cannot pay twice. This is the exercise that teaches idempotency properly.
  4. Add a synced key. Give the planner a new top-level document. Add it to isSyncable, confirm readLocalDoc picks it up, and write a merge test for two devices editing it on the same day. Every skill in this tour, in one feature.

Habits that separate professionals from hobbyists

  • Read the error message. Slowly, to the end. It usually names the file and the line. Most beginners guess instead of reading; that single habit costs years.
  • Pull rules out of components. This repo is the proof: 181 tests, none of them touching the UI, and the UI is the part nobody is afraid of.
  • Never compare objects with JSON.stringify. You have now seen what it costs.
  • Write the reason down where the code is. The comment above PUSH_DEBOUNCE explains why it is 4000 and not 2500. Without it, someone “tidies” it back to 2500 next year and the loop returns.
  • When you cannot explain it, you do not understand it yet. Try explaining mergeState out loud, including why the tombstone wins a tie. The gaps announce themselves.
